# FrilVault Knowledge-Layer Instructions

Scope: `.vault/**` only.

Generated by FrilVault v{{FRILVAULT_VERSION}}.

This file describes safe operations on FrilVault knowledge metadata. The
`.vault/**` directory is not project source code. For repository-wide coding,
build, test, and style instructions, follow the repository root or nearest
applicable `AGENTS.md`. This file does not grant permission to modify source
files. If instructions interact, follow both and apply the more restrictive
data-safety rule.

## Purpose and boundaries

- FrilVault stores persistent notes beside source code without modifying source
  files.
- Paths and anchors in notes may refer to source code, but they remain Vault
  metadata. Never change source code merely to attach or update a note.
- Read Vault metadata to understand implementation notes, decisions, TODOs, and
  developer intent. Keep note content factual, concise, and tied to real code.

## Data model

- `<vault-root>/workspace.json` stores workspace metadata, including the
  top-level `mode` (`local` or `shared`) and workspace settings.
- `<vault-root>/notes/<source-file>.json` stores the notes for a workspace-
  relative source file. Each file has a `notes` array.
- A note has a stable `id`, an `anchor`, Markdown `content`, optional `tags`,
  optional image `attachments`, and UTC `created_at` and `updated_at` values.
- Attachments are stored under `<vault-root>/images/<note-id>/`.
- Preserve existing IDs, timestamps, unknown fields, and unrelated notes. Do
  not rewrite the whole Vault for a one-note change.

## Recommended workflow

1. Read the repository `AGENTS.md` and this file before changing Vault data.
2. Inspect existing notes and tags before creating or editing one.
3. Prefer the CLI whenever an equivalent command exists:
   `flvt list --file <path>`, `flvt add`, `flvt update`, `flvt delete`,
   `flvt search`, `flvt attach`, and `flvt status`.
4. Use direct JSON edits only as a carefully validated fallback. Never silently
   delete unrelated notes or create duplicate note IDs.
5. Validate the result with `flvt status`, `flvt doctor`, and a focused
   `flvt list --file <path>` or `flvt search` command.

Source-file paths passed to the CLI are relative to the workspace root. The
workspace root and Vault Path are distinct: an explicit `--vault <path>` or a
nearest discovered `.vault` may place metadata outside the source tree.

## Anchor rules

- Use a Line Anchor for an exact 1-based line and column. A blank line inside a
  function is still a line anchor when the note belongs to that location.
- Use a Symbol Anchor when the note belongs to a named function, method, struct,
  enum, trait, or impl and should be re-resolved after source edits. Include the
  symbol kind, a useful signature when available, and an optional 1-based
  `line_hint` when duplicates are possible.
- Do not turn a line anchor into a symbol anchor merely because the line is
  inside a symbol. If a symbol cannot be resolved, report it rather than
  changing source code or inventing a new anchor.

## Tag rules

- Reuse existing tags before adding a new one.
- Tags are trimmed, have at most one optional leading `#` removed, and compare
  case-insensitively for duplicates. Keep one consistent spelling.
- Avoid duplicate forms such as `todo`, `TODO`, and `#todo`. Prefer concise,
  reusable labels such as `architecture`, `decision`, `todo`, `refactor`,
  `performance`, or `security`.

## Safety and validation

- Never store secrets, credentials, or private keys in notes.
- Never add comments, markers, generated blocks, or imports to source code just
  to attach a note.
- Preserve unknown data and unrelated files. Do not silently replace or delete
  user-customized `.vault/AGENTS.md` content.
- Confirm that the Vault loads, the source path is valid, the anchor is valid,
  the note content exists, and unrelated notes are unchanged after a write.

## Local and Shared Vault modes

- `flvt init` creates Local mode by default; `flvt init --shared` opts into
  Shared mode for a new Vault. Re-initialization preserves the existing mode.
- Local mode uses repository-local `.git/info/exclude` behavior. Shared mode
  leaves the Vault trackable by Git. Do not change modes or Git rules as a side
  effect of editing a note.
- `flvt init` creates this file at the selected Vault Path only when it does not
  exist. Re-running initialization preserves customized content byte-for-byte.
